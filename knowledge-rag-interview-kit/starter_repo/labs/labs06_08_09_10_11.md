## 1. Lab 6：Neo4j + GraphRAG

### 为什么还有图？

Vector 搜索擅长“哪段话与问题相似”；图擅长“从某个实体沿显式关系走几步”。
例如 `Acme → signs → Contract C-101 → hasCounterparty → Bluebird`。
问题“Acme 的合同关联哪个客户？”需要两跳。图给出关系与每条边的原文出处；不靠模型凭空推理。

最小 ontology 在 `app/dto/graph.py`：

```text
Company --owns--> Subsidiary
Company --signs--> Contract --hasCounterparty--> Customer
                          --affects--> Account
AuditFinding --relatesTo--> Risk
```

这是 Lab 6 所需的最小 Lab 5 前置定义；没有顺带实现完整 ontology 编辑器或 Lab 7 实体消歧。
Entity 有 canonical ID、name、type。Relation 必须引用存在的实体，并符合允许的端点类型。

### 先抽取，再人工检查，再写图

```sh
curl -X POST http://127.0.0.1:8000/graph/documents/<DOCUMENT_ID>/extract
```

Ollama 返回 `entities` 与 `relations`。每条关系必须附带原文中的连续引用，Pydantic 校验 schema。
抽取、评估与 agent 使用 [Ollama structured outputs](https://ollama.com/blog/structured-outputs)，
把 JSON Schema 传给模型服务约束输出，再在服务端二次校验；仅要求“返回 JSON”仍可能得到错误结构。
审阅输出后，把 JSON 原样或修订后提交：

```sh
curl -X PUT http://127.0.0.1:8000/graph/documents/<DOCUMENT_ID> \
  -H 'Content-Type: application/json' --data-binary @extraction.json
```

无效类型、缺失端点、无法在原文定位的引文被拒绝。**引文存在并不证明关系理解正确**，所以保留人工审阅步骤。
模型不会生成并执行 Cypher。应用只执行固定的参数化查询，避免任意 Cypher 注入。
Neo4j 使用当前 async driver 的 managed transaction，写同一份文档会事务性替换该文档的子图。
驱动参考：[Neo4j Async API](https://neo4j.com/docs/api/python-driver/current/async_api.html)。

### 查询两跳与比较 vector

```sh
curl -X POST http://127.0.0.1:8000/graph/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"Which customer is connected to Acme through its contract?","entity":"Acme","hops":2,"generate_answer":true}'

curl -X POST http://127.0.0.1:8000/graph/compare \
  -H 'Content-Type: application/json' \
  -d '{"query":"Which customer is connected to Acme through its contract?","entity":"Acme","hops":2}'
```

`paths` 返回每条扩展边的 hop、source、relation、target、document_id、evidence。
这里的 paths 是分层扩展得到的边，不是所有路径的枚举；最多 3 跳、30 条结果，每层最多读取 200 条边。
方向会保留在输出中，遍历允许从任意端点扩展。compare 同时返回 vector-only 结果。
如果需要最终生成答案，设置 generate_answer；引用编号对应 graph citations。

Neo4j Browser：`http://127.0.0.1:7474`，只用于开发观察：

```cypher
MATCH (a:LabEntity)-[r:FACT]->(b:LabEntity)
RETURN a,r,b LIMIT 50;
```

节点按文档隔离，跨文档靠 canonical ID 扩展；检索只读取 PostgreSQL 允许的文档子图。
“Acme”和“ACME Inc”是否相同仍需人为给同一个 canonical ID，自动 entity resolution 属于 Lab 7。
删除文档后旧图节点可能暂留，但不再能被 API 检索；此版没有后台图垃圾回收。

代码阅读：`api/graph.py → dto/graph.py → services/graph.py`。

## 2. Lab 8：知识资产、生命周期、引用与回滚

PostgreSQL 的 `platform_records` 保存资产快照、审批/修改人、时间与原因。
知识原文仍是不可变 documents；本版 version 是**治理元数据快照版本**，不是文档在线编辑器。
修改文档正文请创建新的 document，再登记和发布；不会把新正文偷偷覆盖到已批准证据里。

```sh
curl -X PUT http://127.0.0.1:8000/governance/documents/<DOCUMENT_ID> \
  -H 'Content-Type: application/json' \
  -d '{"source_uri":"lab://policy/017","source_owner":"HR","business_owner":"People Team","effective_date":"2026-01-01","expiry_date":"2027-12-31","security_level":0,"confidence_score":0.95}'
```

返回 draft。接着每一步调用 `/governance/documents/<DOCUMENT_ID>/transition`：

```json
{"action":"validate","reason":"Checked ownership, dates and source"}
```

然后 action 分别是 approve、publish。必须按顺序：

```text
draft → validated → approved → published → deprecated
           editor      approver    approver      editor
```

admin 可执行全部动作。validate 校验结构与日期，不是模型自动证明文档正确；approve 是用户的审阅决定。
每次状态修改产生新版本，GET 资产可查看 history、parent_version 和 provenance_chain。
已发布资产重新 PUT 会变为新 draft，需要重新批准；严格治理开启时，它暂时不参与检索。

回滚：

```sh
curl -X POST http://127.0.0.1:8000/governance/documents/<DOCUMENT_ID>/rollback \
  -H 'Content-Type: application/json' -d '{"version":1,"reason":"Restore previous ownership metadata"}'
```

回滚不会删除历史，而是以旧字段创建新 draft，防止绕过审批直接复活过期知识。
`GET /governance/freshness` 给出 usable、freshness_lag_seconds、freshness_score。
score 是简单的“最后治理更新后 30 天线性下降”，不是知识真伪概率，也不等于正文变化检测。

```sh
python scripts/check_freshness.py
```

这是一次性监测命令：有过期/未发布/低新鲜度资产时退出 1；可交给你选择的调度器定时运行。
本次不会悄悄为你创建周期任务。

`POST /governance/citations/validate` 示例：

```json
{"document_id":"<DOCUMENT_ID>","text":"Full-time employees receive 20 days of annual leave each year.","version":4}
```

检查文档存在/可读、引文是否来自原文（忽略空白差异）、版本是否当前；严格治理开启时再检查发布与有效期。
RAG 引用同时带 version、source_uri，便于追溯。
冲突策略：此版只按权限、发布状态与日期排除不可用知识；不会自动裁决两个均已发布的相互冲突政策。
需要 source authority ranking/冲突处理时应扩展 Lab 7，不应让模型随意选一份。

代码阅读：`dto/governance.py → services/governance.py → repositories/platform.py`。

## 3. Lab 9：检索与生成分开评估

Lab 4 的 `eval/run_eval.py` 继续用于纯 retrieval baseline 比较。
Lab 9 新增 `/evaluation/run`，dataset 包含 query、expected_sources、expected_facts、allowed_answer、forbidden_answer。

```sh
python eval/run_generation.py eval/lab9-dataset.json --output eval/baseline.json
# 复制上次打印的 id；后续改 prompt/retrieval 后重新运行
python eval/run_generation.py eval/lab9-dataset.json \
  --baseline <BASELINE_ID> --output eval/candidate.json
```

输出：Recall@K、MRR、NDCG@K、Precision@K、answer relevance、faithfulness、correctness、citation accuracy。
前四项是确定性排名指标；三个回答指标由本地 Ollama 按 0–1 打分；citation 检查编号、预期来源和原文引用。
forbidden_answer 是大小写不敏感的禁止短语检查，不是完整的语义安全评估。
`judge:false` 可关闭模型评审，此时不返回那三项指标，避免用伪数字冒充 faithfulness。

baseline 必须属于当前身份，并使用相同 dataset、K、judge 设置；默认允许下降 0.05。
依赖失败单独记为 failure，并使 passed=false，不能把失败查询静默跳过后宣布回归通过。
CLI 在失败/回归时退出 1，方便加入 CI。首次无 baseline 的 passed 只说明执行/禁止短语检查通过，不代表回答达到业务质量门槛。
同一个模型回答又评审存在偏差；小样本只适合演示，正式验收需要人工标签与独立评审。

代码阅读：`services/evaluation.py`、`evaluation/metrics.py`、`eval/run_generation.py`。

## 4. Lab 10：可观测性、安全与预算

`GET /observability/metrics`：请求 P50/P95、查询 P95、检索/LLM P95、错误率、token、估计成本、索引延迟、新鲜度。
`GET /observability/traces`：最近 50 条请求中的阶段耗时与错误类型；响应头 X-Trace-ID 可定位单次请求。
trace 不记录 query、原文、完整回答、bearer token；私有 agent observation 存在受 API 权限保护的 PostgreSQL 中，不输出到普通日志。

这是进程内最多 500 条记录的学习版 tracing，**不是 OpenTelemetry exporter，也不是生产月度 SLO 统计**。
进程重启清空指标；多个 worker 不聚合，所以请用单 worker。
token 来自 Ollama 返回的 prompt_eval_count/eval_count；成本是配置单价估计，不含 GPU、电力、硬件折旧。
老版本已索引但没有 indexing marker 的文档会显示 unindexed；重新 index 后补齐 marker。

### 开启 RBAC / ABAC / ACL

先停止旧 controller，再在同一终端配置。下面 token 仅作本地示例，不能用于生产：

```sh
export SECURITY_ENABLED=true
export API_IDENTITIES='{"demo-admin-token":{"user":"alice","role":"admin","tenant":"local","clearance":3},"demo-reader-token":{"user":"bob","role":"reader","tenant":"local","clearance":0}}'
RAG_ENABLED=true GRAPH_ENABLED=true sh scripts/start_local.sh
```

API 使用 `Authorization: Bearer demo-reader-token`。Swagger 右上角 Authorize 可填写 token。
当前普通前端尚未提供登录/携带 token 的 UI；安全模式请用 Swagger/curl，不要把 token 放 URL。

- RBAC：reader 只读/查询；editor 写文档/治理草稿；approver 审批发布；admin 管理。
- ABAC：metadata.tenant 必须匹配身份 tenant，security_level 不得超过 clearance。
- 文档 ACL：metadata.acl 是允许读取的用户名列表；空列表表示该 tenant 内符合密级者都可读。
- 管理员可绕过同 tenant 内 ACL，但不能跨 tenant 读取。
- security_level 优先取资产 registry，否则取 document metadata。
- 安全模式完全禁用 raw Redis/ES inspectors（缓存/索引可能混有多个 tenant）；改用有 ACL 的文档接口。
- metrics/traces 只允许 admin；聚合 metrics 是实例级指标，trace 不含证据正文。
- `/search` 的缓存 key 包含计算后的允许文档集合；不是全体用户共享无权限区分的结果。
- RAG 在 BM25/Qdrant 候选生成时加入服务端允许文档 IDs，reranker/LLM 不先看无权资料再过滤。

创建文档示例 metadata：`{"tenant":"local","acl":["alice"],"security_level":2}`。
客户端不能通过提交 metadata.tenant 冒充其他 tenant；创建时服务端使用认证身份覆盖它。
请验证 reader 的 direct GET、list、search、rag/hybrid 都不返回该文档，而不是只测其中一条路径。

本机 demo 默认不启用身份认证，不要直接暴露到公网。现有 Postgres/Redis/ES Docker 端口也没有生产认证；
生产应加网络隔离、TLS、身份提供方、密钥管理、速率限制、持久化 telemetry 与独立管理员审计。
对这种本地数据量，服务端扫描文档来计算 allowlist 是有意的简单实现，不适用于大规模语料。

### “回答质量下降”排查清单

1. 保存 X-Trace-ID 与请求参数，不把敏感原文贴进公开日志。
2. 看 dependency warnings、retrieval/LLM latency、index/freshness lag。
3. 用同一 golden dataset 对比 bm25/vector/hybrid，先判断召回是否下降。
4. 检查 ACL、发布状态、日期、embedding 模型/collection 是否变更。
5. 如果检索正常，检查 context 截断、prompt、模型与引用；再运行生成评估。
6. 回退有问题的配置，重新跑 baseline，确认恢复后再发布；不要仅通过增加 top_k 掩盖根因。

## 5. Lab 11：不靠框架的 Agent

```text
goal + observations
  → Ollama 选择结构化 action
  → Pydantic 校验 tool allowlist / arguments
  → application 执行工具
  → 校验结果 → observation → 下一轮
  → finish / max_steps / timeout / budget_exceeded / failed

create_follow_up → awaiting_approval → 人工 approve → 幂等写 PostgreSQL → 继续
                                  └→ reject → 不写入
```

三个工具：search_knowledge（只读、调用同一条 ACL-aware hybrid）；calculate（只读、安全算术 AST）；
create_follow_up（internal_write，只创建本地待办，不发邮件，不调用外部系统）。
外部副作用属于更高风险，但此版 allowlist 不提供此类工具。

```sh
curl -X POST http://127.0.0.1:8000/agent/runs \
  -H 'Content-Type: application/json' \
  -d '{"goal":"Use calculate to compute (1200 * 0.15). Then finish with the result.","max_steps":4}'
```

查看返回 steps/status/answer。然后尝试：

需要强制“先检索再计算”时，请加 `"required_tools":["search_knowledge","calculate"]`。
这是可选的确定性前置步骤：模型仍生成工具参数，但不能跳过工具直接猜答案。
真实验证中小模型曾跳过 calculate 并猜错金额，因此不应只依赖 prompt 约束重要步骤。
默认空列表保留自主工具选择，适合对比 agent 与 deterministic workflow 的差异。

```json
{"goal":"Search for annual leave policy. Create a follow-up to verify the policy with HR. Do not claim the follow-up exists until approval."}
```

返回 awaiting_approval 时，在 `/agent/runs/{run_id}` 检查 pending.arguments，确认标题与描述。
审批端点不接受修改 arguments，只批准已经展示的那一次操作：

```sh
curl -X POST http://127.0.0.1:8000/agent/runs/<RUN_ID>/approval \
  -H 'Content-Type: application/json' -d '{"approved":true}'
```

`approved:false` 进入 rejected。`GET /agent/followups` 查看当前用户的本地待办。
幂等键由 run_id + validated arguments 计算，PostgreSQL 唯一键确保重复批准不会重复写同一个动作。
待审批状态保存在 PostgreSQL，重启后仍可批准；这个基础实现不是 Lab 12 的任意步骤崩溃恢复状态机。
安全模式下 run 只对同 tenant、同 user 可见；批准还要求该 user 使用 admin/approver 角色的身份。
这版未实现另一个用户代审批的工作流、审批过期和外部系统补偿。

预算：最多 12 steps；默认 6。默认累计执行 120 秒（审批等待不计）；只读工具最多重试 1 次。
生成调用使用 UTF-8 字节数 + 输出上限做保守 token 预留，不是精确 tokenizer；实际 token 在 observability 查看。
默认 token_budget=50000、cost_budget=1；本地单价默认 0，token/step/time 上限仍然有效。
预算在每次 agent 规划前检查；检索 embedding 没有额外云 API 费用，预算不是整台机器的算力计费器。

### 五个 golden task

| Task | 期望工具轨迹 / 验收 |
|---|---|
| 计算 `(1200*0.15)` | calculate → finish，结果 180 |
| 查年假天数 | search_knowledge → finish，引用/内容支持 20 天 |
| 查合同再算 15%，required_tools=[search_knowledge,calculate] | search_knowledge → calculate → finish，金额 180 |
| 创建本地 HR follow-up | awaiting_approval 之前没有写；批准后只有一个结果；重复批准仍一个 |
| 相同写操作但拒绝 | rejected，followups 数量不增加 |

再故意设置 max_steps=1、timeout_seconds=5、token_budget=1000，观察安全终止而不是无限循环。
也可以执行 `python eval/run_agent.py` 跑五个 API golden task；会留下一个带 Lab 标签的本地待办。
安全模式下使用有审批能力的 API_TOKEN。脚本验证工具轨迹、关键答案以及重复审批/拒绝没有额外写入，失败退出 1。
小型本地模型不保证每次选择正确工具；trace 的意义是把失败暴露出来，不是把错误答案包装成成功。
工具选择失败应改进提示/模型或使用确定性 workflow；不能扩大任意工具权限来迁就模型。
